# Engine design

This guide explains how the shared engine (`include/`, `src/`) reproduces the
cartridge. [Architecture](ARCHITECTURE.md) covers the Nintendo 3DS adapter
around it.

## Source ticks and presentation

UltraStarFox's `transfer_l` runs `dostrats` once for each completed game frame,
and `dostrats` increments `gameframe` before it updates the object strategies.
The original pipeline spreads that work over three IRQ phases of the 60 Hz
raster, so the game advances at most 20 times per second. Running the whole
loop once per presented frame would make movement, map waits, attacks, damage,
random numbers and animation run several times too fast.

The engine therefore separates the two clocks:

```text
sample real time and input
        |
        v
source tick (up to 20 per second) ---> previous / current snapshots
        |                                         |
        |                                         v
        +--------------------------------> interpolate (alpha) at the
                                           presentation deadline
```

Input edges are latched until a source tick consumes them: a press and release
between two ticks is not lost. Presentation rates convert through an exact
1440 Hz integer timebase into the 60 Hz cartridge raster, which keeps driving
the deterministic source ticks, frontend sequencing and audio. Floating point
appears only in rendered transforms, matrix interpolation and the interpolation
alpha; game state stays fixed-point and deterministic.

## Running the cartridge code

Game logic is the cartridge's own 65C816 code, not a rewrite. `Wdc65816` wraps
the pinned RetroCPU core in a SNES memory map (LoROM, work RAM and mirrors, the
joypad register). Hardware registers whose behaviour has not been verified keep
open-bus reads; a zero-filled I/O map would change control flow.

- **Compact interpreter.** `wdc65816_lean.cpp` executes most instructions. Its
  opcode handlers are generated by `tools/generate-lean-65816.py` from the
  RetroCPU templates and reproduce them access by access: the same bus accesses
  in the same order, the same flag words and the same cycle counts. Each
  instruction runs in two shared steps (addressing mode, then operation), which
  keeps the code small enough for the Old 3DS 16 KB instruction cache.
- **Native kernels.** `wdc65816_kernels.cpp` replaces a few hot cartridge loops
  with C++ that produces the same memory, registers and cycle counts.
- **Super FX entry points.** Calls into Super FX routines (such as `MCOPYFACE`,
  `SHOWVIEW_L` or `DO_3D_DISPLAY`) are handled on the host: the work that only
  produces pixels is done by the renderers from the same state, and the state
  the presentation needs is captured at the call.
- **Object bridge.** `MapVm` keeps the cartridge's object records (`alblks`,
  56 bytes in the original game and 57 in Star Fox EX, with the active and free
  lists) in a typed `ObjectPool`. Before native code runs, the bridge writes
  back only objects the host changed; afterwards it reads back only records the
  code wrote, using write marks instead of comparing whole tables. Starting a
  map invalidates every copy.

Map scripts, predicates and strategy code run through this path with their
original side effects. `PathVm` and `Prng` are host reference models of the
cartridge's PATH interpreter and random generator, used by tests.

## Models and rendering

Shapes are decoded from the assembled cartridge data, not from the readable
sources, because assembler conditionals, symbol expressions and custom point
and wireframe macros change the emitted bytes. The decoded form keeps signed
8- and 16-bit coordinates with each header's shift, animated point sets, faces
of 2 to 12 vertices and wireframe edges, visibility normals and BSP order,
colour tables, lighting modes and texture IDs, shadow and LOD references, and
collision bounds.

The software renderer is a C++ translation of the Super FX shape interpreter
and rasterizer. It draws into an indexed framebuffer with the source face
order, fixed-point matrices, clipping, scan conversion, line rules,
sprite-faces, LOD selection, lighting and depth palettes. It can also record
its output as raster commands: the 3DS compiles them into PICA200 draws, and
replays them on the CPU when the GPU path is not available. PPU
backgrounds, sprites, HUD, colour math and windows form a separate layer and
are never folded into the model renderer.

## Equivalence testing

Exactness is checked against the cartridge, not against appearance:

- Per-tick state digests from deterministic replays must stay identical when
  engine code changes: console snapshots, scripted tours and scenes from
  power-on, for both cartridges.
- A capture's `game-state.bin` and the tour's input script reproduce the logic
  ticks the console ran, with the same 65C816 instruction counts.
- Where the cartridge draws something itself, it is the oracle: the comms test
  decodes the teammate meter from the Super FX bitmap and compares it with the
  host's decision on every frame.
- Interpolated frames between ticks have no original equivalent; they are
  checked for endpoint identity and monotonic motion, not against a golden
  image.

Host results establish exactness, not console speed. See [Testing](TESTING.md)
and [Status](STATUS.md).
